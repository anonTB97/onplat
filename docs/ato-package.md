# ATO package — the skeleton an ISSO assembles from this repository

What an RMF authorization package needs, and where each artifact stands
against this tree: **exists** (with the repository path and the job, command
or test that generates or verifies it), **partial** (what is there and what
is missing), or **missing** (who writes it and from what). The rule the
whole document is held to is the one `docs/production-posture.md` and the
generated `docs/ssp-input.md` already follow: no control is called
implemented without a pointer into the repository that verifies it, and an
artifact is "produced" only when it is a CI artifact or a generated document
at the release tag, regenerated and never hand-edited. The charter's ATO
stream (`docs/programme/charter.md`, A1–A21) is the source of the list;
this document is the working version an ISSO can tick, and it records what
assembling it found to be stale.

Sections: 1 how to read · 2 the artifacts · 3 evidence to NIST 800-53
anchors · 4 the yard's half · 5 assembly at the release tag · 6 findings
from assembling this.

## 1. How to read

- **Exists** means a person can run the named command or open the named
  job's artifact at the release tag and get the artifact. The path is
  given; "generated by" and "verified by" are named.
- **Partial** means the repository produces the evidence and the artifact
  needs prose or a yard-side half to be an artifact; what is missing is
  listed.
- **Missing** means nobody has written it; the row says who does and from
  which repository facts.
- Status vocabulary for controls, from the SSP input: **Implemented** (in
  this tree, with a verification pointer), **Hybrid** (split with the
  deploying environment; the environment's share is named), **Planned**
  (open in `docs/poam.md`).
- Nothing in §3 claims a control family is satisfied. It maps a mechanism
  to the controls it is evidence for, and names what it does not prove.

### 2.8 Incident response procedure — A13

**Missing.** Write it against what the system gives a responder, all of
which exists:

- The HTTP audit stream: one JSON object per `/api` request and per non-2xx
  anywhere, on stdout into the journal (`hardening.rs` `audited`);
  `journalctl -u wadl -o cat | jq 'select(.audit=="http" and .status>=400)'`
  (`deploy/README.md`). Refusals are as loud as successes.
- Backend errors as `{"event":"backend_error",…}` on stderr.
- The ledger: `GET /api/vessels/:id/ledger` re-verifies the chain on every
  read and answers `verified`; `wadl verify-ledger --input <export>` verifies
  an export offline (`crates/wadl-cli/src/main.rs`).
- `wadl support-bundle --out <file>`: a redacted bundle (schema version,
  migration inventory; "no secrets, no PII, no tenant identifiers").
- The proxy's access log for who was logged in (the yard's).

The procedure names: what counts as an incident here (a chain verify that
reads false; a 5xx; a 401/403 pattern from one session; a shed 503 burst; a
document commit nobody signed for), who is called, what is collected (the
journal slice, the ledger export, the support bundle, the proxy log), and
the enclave's IR plan it reports into. The engineer drafts; the ISSO fits it
to the enclave's plan. Request ids that correlate the audit line, the
problem body and the ledger row are S15's; until then the timestamp and
path correlate.

## 5. Assembly at the release tag

Until S17's evidence bundle exists, this is the procedure; when it does,
the bundle is what this list becomes, generated by CI and never edited.

1. Tag the release; record the tag and commit; `GET /health` on the built
   binary for the version and schema fields (S15 adds `version`).
2. `cargo run -p xtask -- gen-ssp --check` and `gen-leak-tests --check`
   green at the tag; copy `docs/ssp-input.md` and
   `crates/wadl-api/tests/generated_leak_test.rs` (with its test count).
3. From CI at the tag: the `check`, `leak-tests`, `migrations` (with the
   `pg_rls` log), `supply-chain`, `sbom` (the SPDX artifact), `air-gap` and
   `self-assessment` job logs; dispatch `reproducible` and archive its hash
   line.
4. `scripts/self-assessment.sh` through the yard's proxy: the output with
   WADL-SA-05 `proxy-asserted` and no FAIL, no WARN.
5. The ledger export at the tag and `wadl verify-ledger --input` on it.
6. The stress entry for the yard's host (`docs/stress-test.md`).
7. `docs/poam.md` at the tag; the data-load record
   (`docs/pilot-playbook.md` §2.5); the rule sign-off table
   (`docs/briefs/safety-authority-sitting.md` §5) or the signed fallback.
8. The drawn boundary diagram, the PPSM table, the cryptography statement,
   the IR procedure and the CM plan as written for this tag (§2).

The bundle's contents list and the commands above are the only things a
person types; every file in it is a regenerated artifact or a signed record.
